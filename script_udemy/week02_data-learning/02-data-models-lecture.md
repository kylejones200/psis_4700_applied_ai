Now that we have talked about data preparation, learning, prediction, and evaluation, we need to slow down and look more carefully at something that often gets rushed. What is data, really? It is easy to treat data as something objective—rows in a table, numbers in a file, text in a document. But data is not reality. Data is a record of observations, and every observation is a simplification. A sensor measures temperature but misses variation. A survey captures an answer, but the answer depends on how the question was asked. A system logs an event, but only the events it was designed to record. So when you look at data, you are not looking at the world; you are looking at a filtered version of the world.

That distinction matters, because models learn from that filtered version. If something is missing, the model cannot recover it. If something is distorted, the model will learn that distortion. So before you build anything, you have to ask a simple question: what does this data actually represent?

Most of the time, data appears in tables. Rows represent cases; columns represent attributes. Each row might be a customer, a transaction, a sensor reading, or a moment in time. Each column describes something about that case. This structure feels natural because it matches how organizations operate. Systems record events, events become rows, and properties become columns. That is why tabular data remains dominant in applied AI. Even when we work with text or images, we often convert them into structured representations so they can fit into this framework.

Within this structure, there are choices that shape what the model sees. One of the most important is granularity. A dataset of daily totals tells a different story than a dataset of hourly readings. When you aggregate data, you smooth out variation and lose detail. Sometimes that is useful; sometimes it hides the very patterns you are trying to learn. So the level at which you measure and store data affects what the model can discover. Another dimension that appears almost everywhere is time. Events happen in sequence, and the order matters. If you ignore time, you may treat events as independent when they are not. That can lead to incorrect conclusions. For example, if you are predicting customer behavior, the timing of past actions often matters more than the actions themselves. So you need to decide whether your data is cross-sectional, where each row stands alone, or longitudinal, where observations repeat over time. In many real problems it is both—you have multiple entities, each evolving over time. That structure is called panel data, and it introduces additional complexity because patterns can vary across entities and across time.

Now let's talk about something that every dataset contains: noise. Not every pattern in the data reflects a real relationship. Some variation is random. If a model treats noise as signal, it will make poor predictions. So part of working with data is learning to separate what matters from what does not. And that is not something a model can do perfectly on its own; it requires judgment.

Consider missing values. Data is rarely complete. Sensors fail, people skip questions, and systems lose records. Those gaps are not neutral; they can hide patterns and distort relationships. So you have to decide how to handle them. Do you fill them in? Do you remove them? Do you treat missingness itself as a signal? Each choice changes the dataset, and each change affects what the model learns. Now layer in errors: duplicates, outliers, inconsistent formats. These are not rare; they are part of almost every dataset. And they matter. An outlier can pull a model in the wrong direction. A duplicate can overweight certain patterns. A mismatch in types can break a pipeline. So data work involves constant attention to these details.

We need to address something deeper. Data reflects human choices. Someone decided what to measure, someone decided how to label it, and someone decided what to include and what to exclude. Those decisions embed assumptions, and those assumptions shape outcomes. For example, if a dataset excludes certain groups, the model will not learn patterns for those groups. If labels are inconsistent, the model will inherit that inconsistency. This is how bias enters the system—not as an abstract concept, but as a direct result of how data is collected and defined. So when you work with data, you are also working with those choices. You have to be aware of them.

A model does not see raw reality; it sees features. Features are representations of the data that you choose. They describe the aspects of each case that the model can use. If an important factor is not included as a feature, the model cannot use it; it is invisible. So feature design determines what the model can learn. Now here is a key point that people often miss: the target comes first. Every model answers a question, and the target defines that question. If you do not define the target clearly, everything else becomes unstable. For example, if you are predicting customer churn, you need to define what churn means. Is it no activity for 30 days, 60 days, or 90 days? Each definition creates a different problem, and the model will learn accordingly. So clarity at the target level is critical.

Once the target is defined, features connect inputs to that outcome. You might include account age, usage patterns, or customer support interactions. Each feature provides a signal. But features can also create problems. If a feature contains information that would not be available at prediction time, the model may appear to perform well during training but fail in practice. This is called leakage. It is one of the most common and most damaging mistakes, because it gives you a false sense of performance. So you always have to ask: when would this information be available? If the answer is "after the outcome," it should not be used.

Consider how features are constructed. Raw data is often messy; features impose structure. You may compute averages, differences, or ratios. You may encode categories into numeric form. Each transformation shapes how the model interprets the data. For example, if you encode categories as numbers, you are implying an order. If that order does not exist, you introduce distortion. So even small decisions in feature design carry meaning, and that meaning affects outcomes.

Models learn relationships between features and targets. If the target is unclear, the model learns the wrong objective. If the features are incomplete, the model learns an incomplete view. If the data is flawed, the model learns flawed patterns. So the quality of the model is determined long before training begins. It is determined by how the data is defined and prepared. This is why experienced practitioners spend so much time on data and features. Not because models are unimportant, but because models cannot compensate for poor inputs.

So let me summarize this in a way you can carry forward. Data is not reality; it is a representation. Features define what the model can see. Targets define what the model is trying to learn. And every choice you make at those levels shapes the outcome. If you understand that, you can approach modeling with clarity. You can see where problems are likely to arise. And you can design systems that are more robust. Because at the end of the day, models are only as good as the structure you build around them.
