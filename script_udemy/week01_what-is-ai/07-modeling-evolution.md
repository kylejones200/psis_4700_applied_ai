I want to start with a simple shift that changes almost everything about how we work with AI. We used to build models; now we use models. That sounds small, but it changes the entire workflow. In the past, if you wanted a model, you started from nothing. You collected data, you chose variables, and you trained something specific to your problem. Today, you often start with a model that already knows a lot. It has seen language, it has seen images, and it has learned patterns from massive datasets. Your job is no longer to teach it everything from scratch. Your job is to ask it the right questions and give it the right context. So instead of building intelligence step by step, you are working with a system that already has general capability. This changes what skills matter, how teams work, and what "modeling" even means. Keep that contrast in mind as we walk through the old world and the new one.

Consider how this used to work. You started with a question, then you collected your own data—often messy, often incomplete. You cleaned that data and spent time fixing missing values and inconsistencies. Then you chose variables and decided what features might explain the outcome. Then you fit a model. You tried different specifications and tested different assumptions. And you cared a lot about simplicity; you wanted the simplest model that explained the data well. That idea is called parsimony. It sounds academic, but it had a practical reason: complex models were hard to train, hard to interpret, and easy to overfit. So the whole process focused on building something precise, controlled, and explainable. The output was a model designed for one specific problem, and if the problem changed, you started over. That was the cost of doing modeling.

Parsimony did not come from preference; it came from constraints. Data was scarce—you did not have billions of examples, you had thousands, maybe less. Computation was expensive; training a complex model could take a long time or require hardware you did not have. So you had to be careful. Simple models reduced the risk of overfitting, which means they were less likely to memorize noise instead of learning real patterns. And interpretation mattered. You needed to explain results to stakeholders, and a simple model made that possible. You could say which variables mattered and why. So parsimony was not only about elegance; it was about survival under limited data and compute. Now those constraints have changed, and when constraints change, methods change.

Let me lay out the full workflow clearly. You define a question, you collect and clean data, you select variables, you fit a model, you interpret coefficients, you validate on a holdout dataset, and then you produce a result. That result is a model tailored to one task. This process is linear—each step depends on the previous one—and it is slow. If anything changes, you often repeat the process. Now compare that to how many of you use AI tools today: you type a prompt, you get an answer, you adjust the prompt. That difference is not only convenience; it reflects a deeper shift in how models are created and used.

Here is the new world. We inherit models; we do not build them from scratch. Foundation models already contain broad knowledge. They have learned from massive datasets across many domains. So instead of fitting parameters, we interact with a system that already has parameters. We adapt it, we guide it, and we ground it in specific data. The focus shifts from training to application, and this changes what teams do. You spend less time tuning models and more time deciding how to use them. This is why small teams can now do work that used to require large research groups. The barrier to entry has dropped, but the need for judgment has increased. Because now the question is not "can we build a model;" the question is "how do we use this model correctly."

To make this even more concrete: in the old world, you estimated parameters. You trained weights based on your dataset. In the new world, those weights already exist; they were trained on massive datasets. You do not see them directly; you interact with them through queries. This is called inference. Inference means you give the model an input, and it produces an output using what it already knows. So instead of learning during your project, the model learned before your project. That is the key shift. You are no longer teaching the model from zero; you are leveraging knowledge that is already encoded inside it. This is why people say "inference replaces estimation."

Compare old and new using language. In the old world, you might build a model to classify text. You count word frequencies, you train something like logistic regression, and you learn coefficients that map words to outcomes. So the model knows that certain words increase the probability of a class. That works, but it is limited. Now look at the new approach. You take a pretrained model like GPT or BERT. You convert text into embeddings. An embedding is a vector that represents meaning. Instead of a table of coefficients, you now have a point in a high-dimensional space. Words and sentences with similar meaning are close together. So meaning is no longer stored as a rule; it is stored as geometry. That is a different way of thinking, and it allows much richer representations.

Now consider images. In the old world, you trained a convolutional neural network on a labeled dataset. You needed thousands of labeled images, and you trained the model to recognize specific classes. If you wanted new classes, you needed new data and retraining. Now look at the new approach. You can call an API that already recognizes thousands of objects. You do not train it; you use it. Your focus shifts to integration: how do you feed images into the system, how do you interpret outputs, and how do you handle edge cases. So again, the work moves away from building models and toward using them effectively. This is the pattern across domains—language, vision, speech. The model already exists; your job is to apply it.

This shift changes how work gets done. Data ownership changes—you still need data, but you use it differently. Small teams can now do advanced work because they do not need to train massive models. Model choice becomes orchestration: you decide which model to use, how to combine them, and how to route tasks. And governance becomes more important. You are not tuning gradients; you are deciding how systems behave, including safety, bias, cost, and reliability. So the center of gravity moves: less focus on model internals, more focus on system design.

Because of this shift, the required skills change. Prompt design replaces feature selection—you no longer spend most of your time choosing variables; you spend time crafting inputs that guide the model. Context curation replaces data cleaning; you decide what information the model should see. Evaluation changes as well; you care about trust, bias, and reproducibility, not only accuracy. And deployment changes; you manage inference cost and latency and think about how often the model runs and how expensive each call is. So the work becomes broader—less narrow optimization, more system-level thinking.

We can take this one step further. Inference itself becomes the focus. You test what these general models can do, you explore their limits, you adapt them to specific domains, and you design guardrails. Guardrails shape how the model behaves; they constrain outputs and improve reliability. So instead of studying how to fit a model, you study how to control and adapt one. This is a different kind of science. It is experimental. You try prompts, you observe outputs, you refine. And that loop becomes central.

Data still matters, but its role has changed. You do not use data only to train models; you use data to ground them. Grounding means giving the model relevant context for a specific task. For example, you might provide documents, records, or domain knowledge. The model uses that context to produce better answers. So data becomes a way to specialize a general model—not to build it from scratch. This is why retrieval systems matter so much today. They connect models to real information and make outputs more reliable.

Now we return to parsimony. In the old world, simpler models were better. In the new world, large models often outperform simpler ones. Complexity does not punish us the same way; we have the compute to support it. So interpretability moves elsewhere. We no longer rely only on simple models to understand behavior; we use tools, we monitor outputs, and we build explainers. So simplicity is no longer the main constraint. Instead, we manage complexity through systems.

The new process looks like this: you select a foundation model, you prepare contextual data, you query the model, you evaluate outputs, you ground results with retrieval or fine-tuning, then you deploy and monitor. This is not a one-time process; it is continuous. The system evolves as you learn. And the output is not a static model; it is a living system—one that adapts over time.

Let me close with a simple statement. We no longer build models; we interact with them. We do not aim for simplicity in structure; we aim for alignment, context, and judgment. That is the new craft, and it requires a different mindset. Less focus on equations, more focus on decisions. So as you move forward, do not ask only how the model works. Ask how you are using it. That is where the real impact lies.
